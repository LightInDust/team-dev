# Contract requirements at the public acceptance boundary

Use this for a task with a written interface/export contract, especially when green tests can miss a weaker real entrypoint. Keep the task's original requirements; do not generalize one project's fields into universal invariants.

Before delegation, put a compact coverage table in the existing `acceptance` field (or an explicitly selected contract file referenced there). Each independently falsifiable requirement needs:

| Requirement | Public path and owner | Observable oracle | Declared check and fault case |
| --- | --- | --- | --- |
| Input identity must match a frozen reference | Actual loader/CLI validator | Independently pinned expected identity | Listed test changes the supplied identity; public call must reject |
| Output belongs to the selected business case | Actual launcher/API entrypoint before accepting output or recording success | Expected business identity from the frozen case selected by this invocation | Supply an otherwise valid result for another case through the real entrypoint; reject it for the identity mismatch |
| Required state survives serialization | Actual export/serializer, then its consumer if relevant | Exact keys, values and permitted null/missing cases from the contract | Listed test checks real output with a mixed valid/invalid fixture |
| Required annotation stays in its permitted region | Checker actually called by export | Saved/rendered bounds after final layout | Listed test moves a required annotation out of bounds; actual gate must reject |

These are examples of row structure, not mandatory requirements for every project. State the real callable/CLI and exact `test_commands` entry plus test case, rather than "covered by tests". When a gate is still being implemented, identify its intended owner; confirm the final call path during review. Mark unresolved rows NOT VERIFIED with the missing evidence. The helper transports `acceptance` unchanged. New preparation adds `worker_acceptance_inventory` to the prompt with local IDs and JSON pointers into that original value; it does not parse this table, split prose or prove coverage.

During implementation and the ordinary Sol review:

1. Trace from the public CLI/API/export to the real validator. A stronger assertion only in a test utility does not make the production/public gate stronger. Put runtime rejection rules at their actual owner; keep independent assertions in tests.
2. For a required rejection, inject a small contract-breaking input/state through that public path and check the specified error/nonzero outcome. Establish a valid baseline, prove the mutation changes the validator's relevant property, and freeze the expected baseline before corruption; swapping identical bytes cannot test hash mismatch. If a size gate precedes a hash gate, a hash-only fault must change content without changing its original length, keeping the original expected size and digest frozen. Updating expected-size metadata to fit a resized corruption moves the baseline; use that resized fixture for the size-rejection case instead. Check the intended reason and actual boundary reachability so an unrelated setup error cannot satisfy the test. Satisfy every preceding gate (identity, hash, presence/type, precondition) with valid values so the fixture reaches the intended branch, and apply each mutation only after final fixture construction; an earlier guard or a helper that rebuilds the fixture can otherwise make the case vacuous. For a mocked failure boundary, assert its expected invocation/count/arguments and provide valid nonempty upstream state so an empty branch cannot bypass it. Follow [model isolation and reachable faults](model-isolation-tests.md) when real model calls are forbidden, including the per-module REQUIRED import policy when specified by the task. For output-only requirements, inspect the actual serialized or saved artifact; do not require runtime rejection if the contract never asked for it.
3. Derive expected values independently from the pinned contract/input — a literal expected value or independently computed number — never a guessed value or one produced by calling the implementation under test. Applying the same implementation normalization or indexing to actual and expected can hide exactly the defect the contract is meant to catch. Pin the numerical convention (such as quantile interpolation) and a small explicit input distribution before calculating the oracle. State the relevant index base/reset, units and geometric meaning: a centroid coordinate is not its distance to another point, and evaluated pairs include rejected decisions rather than only accepted merges. An export check compares required array values, shape and dtype under the actual export's casts and specified equality/tolerance, not only keys or inventory; require byte equality only where the contract specifies it. For rejected updates, trace earlier mutations and derive the expected post-state at the actual rejection point; rejection alone does not imply rollback or a changed median. Observe missing keys separately from permitted nulls and retain all explicitly required states, without inventing stronger source invariants.
4. Use one targeted [gate-adequacy check](#gate-adequacy) for a high-risk requirement: disable its production gate or damage its output in an isolated copy/scoped mock, then verify the same declared regression fails for the intended reason. Never mutate a live candidate or frozen scientific evidence, and avoid exhaustive mutation campaigns.
5. Bind completed rows to the reviewed candidate and actual logs/artifacts. A successful public CLI run proves only its observed execution/output; it does not show that all contract violations would have been rejected. Read real output and inspect saved visuals where the task requires them. Keep target-only acceptance NOT VERIFIED until authorized target evidence exists.

For repeated fault subcases, recreate consumed external response sequences and mutable fixture state per case, restore scoped patches, and assert that each intended boundary is reached. Do not enlarge a shared mock response budget merely to hide state leaking between cases. Match the specified error meaning observed at that boundary, without imposing incidental wording the contract never required or changing production behavior for a guessed message. An unqualified constant, import failure or exhausted mock before that boundary is a test/setup defect, not evidence of the intended rejection.

The matrix is a navigation aid and a review claim, not a completeness oracle. Astra checks that every original requirement has a row; Sol independently checks the public call path and test oracle in the existing review. Keep failed worker runs separate from takeover candidates. A field added after review requires refreshed affected acceptance evidence; it cannot inherit a previous candidate's PASS.

## Exact rejection boundaries

Derive edge cases from the actual contract rather than a validator's current implementation. Two useful patterns, only when those requirements apply:

| Required boundary | Distinguishing public regression |
| --- | --- |
| Exclusively claim a previously absent output directory | Keep an absent-path success case and reject pre-existing empty directories, directories containing only an unrelated sentinel, and other existing path kinds required by the contract. Assert the complete prior entry set and bytes remain unchanged, including no new failure receipt in an unowned directory. Checking only familiar output filenames does not establish ownership; inspect the atomic directory-creation operation too. |
| Half-open original-image coordinates | For the declared convention `0 <= x < width`, `0 <= y < height`, test a valid interior point and exact `x == width` / `y == height` rejection separately, with asymmetric dimensions. Much larger invalid values do not test the equality boundary. If the contract specifies different coordinates or inclusivity, use that convention instead; do not invent a tolerance or conversion. |

Use owned disposable paths and the real public entrypoint under the declared test command. Keep the positive fixture valid through preceding gates so each boundary is actually reached; an unrelated schema error cannot satisfy these cases. This adds no permission to mutate existing user outputs, run extra worker probes or repeat scientific work.

## Acceptance ledger

At handoff, DS reports each indexed requirement separately. A list entry receives `A1`, `A2`, etc.; a nonempty scalar/object acceptance value receives one `A1` pointing to `/acceptance`. IDs are local to a preparation, not stable identities across a fix round. Cross-reference the original text when comparing runs. Missing or empty acceptance produces no rows and is a contract gap, not success. List entries are indexed even if malformed; indexing does not validate them.

Keep implementation and verification statuses independent:

| ID and original obligation | Implementation and public location | Verification and actual evidence | Remaining blocker |
| --- | --- | --- | --- |
| A1: consume the same validated bytes | partial — loader reads again after hashing | fail — declared check/case and target log show mutation accepted | Bind decode to frozen bytes |
| A2: reject invalid input before mapping | complete — real public validator | not_verified — local cases all skipped; target check not yet run | Required target evidence |
| A3: propagate writer failure | complete — exporter boundary | pass — declared target case reached writer once and observed required error | none |

These are examples, not claims about a particular candidate. Implementation statuses are `complete`, `partial`, `not_implemented`, `unknown`; verification statuses are `pass`, `fail`, `not_verified`. Cite files/public symbols, exact declared command and case, execution environment, result/log and candidate identity. Put actual collection/execution/skips/failures/errors in a shared test summary; use unknown where unavailable. Static inspection may support an implementation claim but does not prove runtime criteria. Exit zero with all cases skipped means zero functional execution. Mixed runs can verify only the cases actually executed. A behavioral failure/error in an executed required check stays fail. Inability to run (for example, a missing target interpreter on the Mac) stays not_verified with its exact error/exit recorded, unless the contract explicitly makes missing dependencies a failure; it never becomes pass.

Label each cited observation with its evidence kind and actor; do not hide the distinction in a shared suite count or a final limitations note:

| Evidence kind | Required attribution and limits |
| --- | --- |
| `persistent_test` | Retained test file/case and fixture identity, actual public or helper boundary, exact declared command, runner/environment and saved execution result. A present but unexecuted case remains `not_verified`. |
| `coordinator_check` | Astra's separate check, observed fault/oracle, candidate/input identity and saved result. Link the retained script or replay command when available; disclose missing replay material. Temporary execution is not worker execution or a persistent regression case, even when its recipe is reproducible. |
| `source_inspection` | Inspected file/symbol and source identity. It can satisfy an explicitly static criterion; runtime rejection, boundary reachability and cleanup remain `not_verified` without execution evidence. |
| `none` | No supporting observation; name the missing check and keep verification `not_verified`. |

For each fault branch, separately state `regression_test: present | missing | unknown | not_required`, deriving the obligation from the original contract. `present` requires a retained case exercising the required boundary, not just a similarly named helper test. Use `not_required` only when persistent test delivery is not required; this guidance does not impose new tests on every task. A coordinator-only runtime PASS may establish the observed behavior, but cannot satisfy a contract-required regression-test deliverable: keep that obligation incomplete until an authorized retained test is added and executed. Do not invent a replay recipe for an old result or rerun/expand work solely to improve its classification.

Split fault branches that have different evidence: for example, baseline mutation is not source mutation, a loader rejection is not public-entry rejection, and successful cleanup is not encoder-failure cleanup. List multiple evidence kinds separately under a row or use subrows, with concrete case/log references; "17 tests + 5 checks" does not identify which branch ran. Preserve the original worker ledger and attribute later coordinator evidence in a separate reconciled ledger/addendum. Summaries should report persistent-test coverage, coordinator-only checks, source-only claims and remaining gaps separately; do not say "all pass" while a required branch or retained test is missing. A coverage gap does not by itself diagnose transport/model failure or change the historical worker execution status.

For a compound requirement or selected referenced contract, expand into `A1.1`, `A1.2`, etc. and account for every clause; these subrows are authored and checked by Astra/DS/Sol, not extracted by the helper. Preserve original explicitly excluded work without converting new omissions into exclusions. Before dispatch, Astra should split coupled obligations into independently falsifiable rows and ensure required test files are allowed and required commands are declared. Do not inflate the task to implement later slices; keep their obligations in the coordinator's overall plan.

Old tests are regression evidence, not permission to shrink the written contract. Lack of a case, a fixture needing repair, or an outdated oracle is not scope creep. DS must add/update authorized tests against the contract and use the exact frozen command catalog. If a contract conflict cannot be resolved or needed files/commands are unauthorized, report the exact conflicting clauses, affected rows and blocker, preserving the incomplete candidate. Do not silently weaken expected behavior or run extra probes. Only Astra can decide an authorized scope adjustment and prepare a fresh task; an implementation slice being finished does not finish deferred overall obligations.

Before ordinary `propose` / `apply`, Astra compares the worker's rows and deviations with the original required-regression checklist, including selected contract files. A report that calls a row complete but admits that a required retained case is absent or that a different boundary substitutes for it is an incomplete deliverable. Record `regression_test: missing` for the affected required branch, keep overall acceptance incomplete, and report the production implementation status independently and accurately. Resolve the missing test within the existing bounded repair route; do not carry it forward as merely an environment concern. An explicitly authorized diagnostic target run using an already declared command may still help investigation, but label it as diagnosis of an incomplete candidate, not acceptance; this does not permit extra probes. Preserve the original report rather than editing its claims. This is a coordinator check of evidence and contract semantics, not a keyword-based report parser, new model stage or extra recovery allowance.

Keep two cases distinct: a required case that exists but cannot run locally because its declared interpreter is target-only is `not_verified` with the named target owner; a required case that was never implemented is a source-delivery gap even if the same environment is also unavailable. A source listing or total test count cannot establish the intended fault was injected or its boundary reached. Inspect each required case's mutation against the baseline and its oracle; assigning a value already present is not a negative case. Referenced requirements may need subrows before dispatch, so a broad label such as "drift tests" cannot conceal a missing mid-operation branch.

Astra reconciles the ledger before claiming completion and supplies unresolved rows to the ordinary Sol review. Sol independently traces every claimed completed clause through the real diff/public path and test oracle, checks skipped/failed evidence, and reports omissions or unsupported claims as findings. An omitted row is a gap, never an implicit waiver. Do not require a new reviewer stage. Missing, partial, failed or unverified required rows block full acceptance; retain the original failed/incomplete evidence and record later fixes separately. A normal worker exit and green existing suite are insufficient. The ledger is a self-report and navigation aid; the helper does not parse it or add semantic acceptance enforcement to `finalize`.

## Result claims and saved evidence

Before reusing a worker's numerical or classification statement, bind it to the relevant candidate/input and read the exact saved structured field, label definition and supporting test assertion or independent oracle. A confident final paragraph, suite total or copied ledger is not the result source. Cite the field/path and evidence actor in the reconciled ledger; a test expectation alone does not establish the actual saved result.

If only the prose conflicts while the bound source/input, saved result and independent check agree, preserve the original worker report and add a scoped correction identifying the false statement and supporting evidence. Do not rewrite a historical report or change a successful run to failed solely for that prose discrepancy; do not relabel a failed run after a later correction. If structured artifacts or their identities disagree, keep the affected acceptance unresolved rather than choosing the convenient value. Use existing authorized read tools and saved evidence; this check does not authorize extra probes, experiment regeneration or new scientific calculations. A past quadrant/count correction is an example, not a universal expected value.

A nested run, a successful collection or transport step, or a sub-process exit zero does not override the actual declared test's exit, overall result, failures or errors. Report a nested success and a failing top-level result as distinct facts: preserve the initial failure, keep target evidence separate from the collection step, and never let a green inner step stand in for the acceptance outcome.

## Gate adequacy

Keep the public call, contract-breaking fixture and acceptance assertion fixed while changing only the runtime gate under test. With the real gate, the regression passes because the specified rejection occurs. With the gate replaced by a no-op/bogus-success result, invoke that same regression/assertion: it must fail because the required rejection is missing. For output assertions, mutate the actual returned artifact and retain the independent expected record. Do not mock the oracle, rewrite its expectation or count an unrelated setup/signature failure as detection.

An enclosing adequacy test may finish green only after explicitly observing the inner regression's intended assertion failure (for example, an expected `AssertionError` or an inspected failing test result). Record which assertion failed and why. Merely asserting that the mocked gate returned `passed=true`, checking that the mock was called, or separately showing the unmocked gate rejects input does not demonstrate oracle sensitivity. Keep ordinary valid-input coverage. Use the existing test framework and one bounded case; no additional agent stage or mandatory full mutation suite is needed.

For null/zero/rejected observations, derive the fixture and oracle from the [actual producer semantics](producer-consumer-contract.md#numeric-zero-null-and-rejected-observations). A fully passing suite can still encode the same incorrect normalization as the implementation. Classify confirmed mismatches as semantic/acceptance defects even when tool execution and test receipts are complete; changing reasoning effort or timeout does not repair the missing oracle.

### Directional counts and denominators

For a metric whose meaning depends on direction, write the literal truth-to-prediction transitions, eligible population and counting unit in the existing contract before implementation. False acceptance and false rejection, source and destination, or positive and negative directions are not interchangeable. State how unknown truth and undecided predictions affect the numerator and denominator. Derive these rules from the declared evaluation semantics, not the current predicate or a convenient label name.

A complete confusion table can still hide a reversal: two transitions in each opposing direction give the same pooled count under either predicate. Keep useful aggregate conservation checks, but assert the affected public output for each independently addressable cell or a small asymmetric fixture. Use literal expected counts/populations, not a test-side copy of the production condition. A real integration sample with no distinguishing event cannot replace this direction regression. For grouped outputs, bind expectations to the full required group key so opposite directions cannot cancel across groups.

For an observed reverse/swap or denominator-selection fault, demonstrate sensitivity within the existing test framework: keep the public call, fixture and oracle unchanged, substitute that specific fault in an owned copy or scoped runtime seam, and require the same assertion to fail for the intended metric/cell. Restore the implementation and require that assertion to pass. A changed expectation, unrelated exception or independently invented mutant output is not this evidence. Scope the check to the affected requirement; do not add an exhaustive mutation framework to unrelated tasks.

The small [directional summary example](../assets/directional-metrics/summary.py) has a public `summarize(rows)` function. Its synthetic labels are `alpha`, `beta`, `outside` and unknown truth; predictions are `alpha`, `beta`, `outside` or `None`. It counts `false_accept` only for outside-truth rows predicted as alpha/beta. Its `negative_total` denominator includes every outside-truth row, including undecided ones; unknown truth never enters either count. `total`, `unknown_truth` and `undecided` preserve separate observation counts. These semantics illustrate one explicit contract, not a required taxonomy or denominator for other projects.

[The retained regression](../scripts/test_directional_metrics_example.py) uses 16 separate literal cells, an asymmetric denominator case, and the same public assertion under an isolated reverse-predicate mutation. Its symmetric aggregate control deliberately remains green under that mutation to expose the blind spot. Run it with:

```bash
python3 -B -m unittest discover -s scripts -p test_directional_metrics_example.py -v
```

This example validates the demonstration only. Apply the affected oracle to the real project's public summary boundary under its existing authorization; do not rerun frozen scoring or experiments to manufacture evidence.

## Public launcher identity example

For example, a launcher may select a method from a frozen manifest, call an observer, then save a diagnostic. If that contract binds `object_id` and `station` to the method-specific case, the launcher's real `main` must compare the returned fields with that selected case before accepting the diagnostic or marking completion. Valid input/source/weight hashes establish byte identity; they do not establish that the returned observation belongs to the selected case. These field names are an example, not required fields for every project: use only the business identity and guard decisions fixed by the actual contract.

Exercise wrong-object and wrong-station results through that real `main`, with other required fields valid, and assert the intended rejection plus absence of the success marker. Mock only authorized external heavy execution or OS boundaries while retaining the real selection, validation and output/receipt path. Include contract-required guard-decision mismatches and apply the existing high-risk gate-adequacy check where appropriate. A helper-only identity test or passing core-function suite cannot establish the launcher's behavior.

Record the owner of each finding separately: a coordinator-written launcher can have an integration defect even when the worker/core library is correct. Keep the launcher revision and its public-entry tests bound in the ordinary review, without attributing that defect to a failed worker attempt or relabelling the earlier attempt successful. Add this as a small integration layer when needed; it does not expand the worker's first core slice or authorize rerunning frozen cases merely to improve historical evidence.
