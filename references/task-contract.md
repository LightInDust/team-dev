## SSH command keepalive

If the task requires a particular SSH keepalive, add this bounded configuration to `target` before preparing a new run:

```json
"ssh_keepalive": {"server_alive_interval": 5, "server_alive_count_max": 2}
```

The interval accepts integers 1–300 seconds; the unanswered-probe count accepts integers 1–10. These are helper policy limits. Omitted fields default to 15 and 2; zero, booleans, strings, unknown keys and raw SSH option injection are rejected. A local target must omit `ssh_keepalive`, since it cannot control separate coordinator-issued SSH commands.

`prepare` writes fully resolved values into the SSH target and records `transport_policy` in task and metadata. Start/resume and subsequent target operations check this frozen policy; changing it requires a new run. `status` exposes the saved metadata. Legacy runs without policy records retain 15/2 and reject adding this setting after preparation. Do not hot-edit an active run or retrofit its JSON. Status, cancellation and diagnosis remain available even when policy validation blocks launch or target operations.

These options apply only to helper command connections for source capture, apply, tests and verification. Existing `BatchMode=yes`, `ConnectTimeout=10` and `ClearAllForwardings=yes` stay in effect. This does not edit SSH aliases, established tunnels, OMP provider requests or HTTP proxies. Independently issued SSH/scp commands need their own task-consistent options. Keepalive does not extend command/test/worker deadlines, prove connectivity, or make an unknown remote outcome successful.

## Bounded SSH source capture

Remote source inspection requires an existing POSIX Python 3.9+ available as `python3`, plus Git. The helper sends stdlib-only capture code and a bounded JSON request for that invocation; it installs no OMP, credentials or persistent helper on the server. Missing Python is a preparation blocker, never a reason to revert to ambiguous shell predicates or install a runtime automatically.

`prepare` uses one SSH connection for identity, selected metadata/content and pre/post consistency checks. Remote `identity`, `file` and `manifest` each use one bounded capture invocation rather than opening connections for every field or path component. Apply, target tests and finalization remain separate operations with their existing gates; this change does not turn them into a remote transaction. Existing SSH options and task-frozen keepalive values remain unchanged, including 5/2 when that task specifies them.

The protocol permits at most 100 exact relative paths, 4 MiB per file and 32 MiB total per remote capture, with a 64 KiB request, 48 MiB stdout and 64 KiB stderr ceiling. The outer command deadline remains 30 seconds; individual Git identity commands are capped at five seconds within the helper's 25-second work budget. Limits fail closed without automatic retries or deadline extensions. Output pipes are drained concurrently with size enforcement. No selected file bytes are written into a local run until the entire response and successful transport exit have been validated.

Every selected path component is inspected without following symlinks; descriptor-relative traversal keeps reads anchored to the opened repository. Symlinks (including dangling ones), nested Git markers, nonregular files and inspection errors fail. Only an explicit `ENOENT` at a checked component produces absence; SSH exit 255, other nonzero statuses, permission failures or incomplete JSON never do. Remaining local shell predicates distinguish status 1 from errors. Two sweeps compare contents, modes, file/directory identities and missing-path prefixes; repository identity/HEAD/status and root path identity are checked before/after. The receiver checks the request binding, complete envelope, exact path set, size and payload hashes before publishing a snapshot.

This is an observed consistency check, not a lock against unrelated writers or an atomic filesystem snapshot; transient changes between observations can escape detection. Existing dirty content is captured as before. Preparation transport failure happens before DS dispatch and must retain that classification. Keep historical partial directories as failure evidence; do not hot-edit their metadata, relabel a fallback local-copy workflow as verified remote capture, or rerun business experiments solely to validate this transport change. Validate transport with isolated fixtures; a local transport stand-in does not prove current network or server availability.

## Transport failure during finalization

A successful worker, passed target tests and a saved Sol PASS can still leave delivery unverified if `finalize` cannot capture the current target. Inspect the actual failing operation, exit status and saved state: SSH connection failure during that read is a transport observation, not evidence of an OMP/provider failure, bad candidate or failed tests. It also cannot prove the target is still unchanged. Preserve the error, previous test/review bytes and pending delivery state; do not rerun DS or the business experiment just to replace a failed verification read.

For policy-enabled runs, `finalize` changes delivery to `verification_pending` before checking the target. Simply repeating it from that state does not restore acceptance. If the original authorized route is restored and candidate/test/process/review evidence remains valid and unchanged, revalidate and successfully `record-review` the same saved review before `finalize`, checking each result as described in [exit-gated steps](reviewer-provenance.md#exit-gated-dependent-steps). Preserve the earlier failed invocation separately. New source, environment or contradictory evidence reopens affected tests/review; an uncertain remote test outcome requires inspection before any rerun.

The helper has no per-operation alternate-transport override. A different SSH/FRP route is a separate coordinator operation within the task's authorization, never permission to edit frozen run JSON, silently retarget its SSH alias, disable host-key checking or extend budgets. For an explicitly permitted manual completion through a supplied alternate route:

1. Keep the previously trusted target host-key binding and connection/keepalive bounds for that operation. A key mismatch is a blocker: retain it and verify the forwarding destination or obtain trusted confirmation of an actual key change before reconnecting. Do not erase the old key or accept a newly observed key to make the error disappear. Record an initial mismatch and any later successful connection separately; hostname, GPU inventory or matching files alone cannot replace host authentication.
2. Recheck authenticated target identity, user, repository realpath/HEAD and the complete selected file manifest, including modes and absences, against the applied/tested/reviewed candidate. Bind any relevant imported helpers, inputs and test environment required by the acceptance contract. Host-key success alone is insufficient. Missing or changed evidence leaves affected acceptance pending; it does not inherit the old PASS.
3. Save a separate hash-bound manual completion declaration using [the guarded receipt procedure](reviewer-provenance.md#guarded-coordinator-receipt-publication), with the original run state, failed invocation, alternate-route verification, candidate/test/review bindings and residual limits. State the actual implementer: unchanged DS code with coordinator verification is different from an Astra code takeover. The receipt writer validates review/provenance only. Leave the original run pending and distinguish manual acceptance from helper `verified`; a task that specifically requires successful helper finalization remains blocked until that gate succeeds.

This is a manual recovery procedure, not automatic failover or a new transport schema. Keep private hosts, routes and raw evidence outside the public skill repository.

## Snapshot and scratch protection

New `prepare` calls set `snapshot_guard_version: 1` and freeze the deletion policy in metadata. `allowed_deletions` defaults to `[]`; if the authorized change needs to remove an existing source file, list its exact path both here and in `allowed_paths`. Every deletion entry must exist in the baseline. A path being editable does not by itself declare its deletion. Do not delete source directories or the snapshot's `.git`.

The worker prompt requires disposable fixtures to use a context manager for **unit tests, manual smoke checks and public CLI invocations alike**. All writes, consuming subprocesses and assertions must finish inside that same scope. For example, adapt the real CLI/arguments below and run inline or from a declared test file:

```python
from pathlib import Path
import subprocess
import sys
import tempfile

snapshot = Path.cwd().resolve()
scratch_parent = Path(tempfile.gettempdir()).resolve()
if scratch_parent == snapshot or snapshot in scratch_parent.parents:
    raise RuntimeError("Choose a scratch parent outside the snapshot")
with tempfile.TemporaryDirectory(prefix="team-dev-", dir=scratch_parent) as tmp:
    fixture_root = Path(tmp)
    output = fixture_root / "output"  # Leave absent if the CLI requires a new dir.
    subprocess.run(
        [sys.executable, "-B", "path/to/actual_cli.py", "--output", str(output)],
        cwd=snapshot, check=True, timeout=60,
    )
    # Assert the actual output contract here, before leaving the context.
assert not fixture_root.exists()
print(f"scratch: {fixture_root}; cleaned after context exit")
```

Keep scratch data outside the snapshot; keep project tests in declared allowed files or use inline checks. Do not create extra validation scripts in the repository. Do not add shell recursive cleanup or hand-written `rmtree` for temporary test data. In particular, never build a deletion target from the current working directory, glob/`ls | head` results, or a command substitution that can be empty. If cleanup ownership is uncertain, leave the artifact and report it. The example is guidance for worker-owned scratch; it does not replace the original acceptance commands.

Do not use fixed `/tmp/<task>` paths, unmanaged `mkdtemp`, a background process or later tool invocation that outlives the context. Context cleanup handles normal exit and Python exceptions; it does not guarantee cleanup after SIGKILL, host failure or escaped child processes. If an existing accepted command creates unmanaged scratch, report the incompatibility and adapt the declared check before running it, rather than silently treating manual checks as exempt. Task-authorized retained evidence belongs at an explicit evidence destination and must be reported as retained, not cleaned scratch.

The worker's completion report must name scratch paths and cleanup status (`cleaned`, `authorized retained evidence`, `residual`, or `unverified`; `none` when unused), then separately list all known constraint deviations and unresolved items. A natural `agent_end`, green tests, or a claim that a leftover is “harmless” does not establish compliance. A residual/unknown path is not authorization for recursive cleanup. Preserve existing evidence and ownership boundaries.

Astra includes this report plus [actual tool evidence](#actual-tool-evidence-and-test-environment) in Sol's ordinary review; no additional review agent stage is required. Check manual commands as well as committed tests. Compact logs omit raw tool arguments; disclose missing coverage instead of claiming they prove the exact command or absence of residue. In the existing review `findings`/`limits`, distinguish code correctness, process deviation, and whether it remains blocking. Correct a remediable issue within the authorized scope; otherwise retain the deviation with an explicit disposition. Do not waive an explicit task requirement on the worker's behalf or call the full task compliant while it remains unresolved. A later accepted candidate does not erase the earlier violation. These are reporting/review obligations: the helper does not parse natural-language constraints, inventory arbitrary host temp paths, or add a filesystem cleanup gate to `finalize`.

Guarded runs inspect the snapshot before starting OMP, roughly once per second while running (including active tools), after tool-end events, and before accepting a terminal event. Each Git subprocess is bounded at five seconds, so the polling interval is not a hard reaction-time guarantee. The scan covers tracked differences against the captured commit and non-ignored untracked files. An observed out-of-scope addition/modification/deletion fails with `snapshot_scope_violation`; an undeclared allowed-path deletion fails with `snapshot_undeclared_deletion`. Missing root/`.git`, changed HEAD and scan failures also stop the run with distinct reasons. Failure evidence is written before abort/cleanup. `resume` checks integrity before archiving prior evidence; `propose` checks again before staging a patch.

This is post-change detection, not tool interception or OS isolation. A fast command can damage the entire snapshot before the next check, and transient changes between scans or ignored scratch files may escape observation. The guard cannot prevent changes elsewhere on the host, and the existing process/file-scope setup must not be described as a sandbox. Keep the real target behind the apply gate. On snapshot damage, retain the original failed/cancelled run; recover candidate text only into a separate coordinator-owned directory, then recheck exact scope, original tests and Sol review. Do not mark a damaged worker successful or silently restore over its forensic evidence.

Already-prepared runs without a snapshot guard retain their previous behavior, including a bounded resume. New preparation enables the guard. Do not edit an active task's JSON to retrofit it. The effort/budget policy and real target state are unaffected by this guard.

Successfully prevented calls stay outside executed-request audit counts; Sol must explicitly resolve them. Third-denial attempts cannot pass. The failure-only `gate-lockout-evidence.json` correlates non-Bash lockouts to raw and compact RPC records as `matched`, `incomplete` or `mismatch`; interrupted/missing delivery remains incomplete, never a completion claim.

Before recording a passing review, use `process-evidence --run /absolute/run` after target tests to obtain the current binding of exact event bytes, the private tool journal, derived audit and `tests.json`. Sol inspects actual arguments/results, the task constraints and target-test evidence, then adds `effort: "max"` and `process_review` to its normal review. That object needs `verdict: "pass"`, the exact `binding` object and a nonempty `reason`. If shell syntax was unsupported/over-limit it also needs `coverage_resolution`; temp-path cues require `temporary_path_resolution`. These fields must explain actual evidence, not merely acknowledge a warning. Missing parameter/result evidence cannot be waived with prose. `unresolved` or `violations` cannot pass. If code is acceptable but process is not, preserve that distinction in findings and an independent takeover receipt; do not label the original run compliant.

Copy the **entire JSON output object** of `process-evidence` into `process_review.binding`, including nested `audit`, `async_execution` for v2/v3/v4, `live_output` for v3/v4, and `preexec_gate` for v4. Copying scalar hashes/counts alone is incomplete even when each copied value matches. Do this while Sol constructs the review after inspecting the same evidence, not by automatically replacing the binding on an earlier PASS. If recording fails, retain the original review and error; let Sol inspect the current evidence and save a separately named corrected review. A genuinely changed journal, candidate or test receipt requires fresh review of the change. The mismatch diagnostic lists expected missing/changed field paths and an unexpected-field count without printing private values or supplied extra keys; it does not repair or relax the comparison.

Count test attempts from actual Bash requests/results and target-test receipts, keeping tool-call IDs and observed outcomes, including earlier failed invocations. Do not use a worker's final “single test invocation” claim as the count. A background acknowledgement and its later notification belong to one invocation, and an unknown exit remains unknown. Distinguish worker invocations, helper target-test commands, test cases collected, OMP API retries, and a resumed worker attempt. Quoted/compound commands can require manual inspection; do not turn missing coverage into zero attempts. Preserve contradictory claims and the failed history separately from a later passing candidate.

Version 2 additionally requires `process_review.async_jobs` (an empty list when no jobs occurred), with the per-job outcome and bound coordinator lifecycle receipt described in the linked async procedure. Missing terminal notification, uncertain resource disposition or a worker cleanup assertion alone cannot satisfy that gate. Zero Python-guard observations under `unsupported_syntax`, including a quoted dependency import, still require manual inspection of the exact invocation and task-specific interpreter/environment constraints; they do not prove explicit `-B`, no bytecode writes or compliance.

Automatic target-test receipts require direct argv. Explicit shell/SSH test wrappers are rejected during new preparation and again at test/acceptance; use the helper's SSH target transport to run direct remote argv, or a separately documented manual/takeover workflow. The measured status is that of the declared test process, not every descendant: custom scripts/runners must propagate their required tests' status and remain subject to source review. Do not replace a supplied test framework or fabricate a runner. stdout and stderr are saved separately in full as received, with real exit code, transport-completeness status and hashes in `tests.json`; a transport timeout retains received partial bytes but has no known target exit code and cannot pass. Worker console tails/pipelines are never authoritative target-test evidence.

New worker prompts also derive `worker_logged_test_commands` and `worker_test_log_root` for [large local test output](worker-test-output.md). These are prepared prompt values, not user-supplied task fields or replacements for `test_commands`. The output-saving shell envelope preserves exact worker argv and status in unique private evidence directories; its command syntax remains subject to ordinary manual process review. These worker logs do not replace the helper's direct target-test receipts or add an automatic log-verification gate. Existing prompts/runs are not rewritten.

`record-review` and `finalize` recheck these bindings and log hashes. After policy validation, a finalization attempt changes a prior `pending_finalization` or `verified` state to `verification_pending`, so changed/missing logs cannot leave a stale PASS. Other states, including `changes_requested` and `tests_failed`, remain intact on failure. A retest still requires fresh review. The checks establish evidence completeness/integrity plus a recorded reviewer judgment, not automatic semantic correctness, host-wide scratch ownership or authentication against same-user JSON tampering. A later source or review change invalidates its earlier binding; retain original failed/retracted evidence.

Execute finalization only after `record-review` has succeeded **and** its recorded verdict is `pass`; a successful recording of `changes_requested` is not permission to finalize. Do not queue both commands unconditionally. For example, this coordinator sequence propagates a recording failure and checks the returned verdict (substitute actual absolute paths):

```python
import json

helper = "/absolute/skills/team-dev/scripts/team_dev.py"
run = "/absolute/run"
review = "/absolute/sol-reviewed.json"

    text=True,

if recorded.get("verdict") == "pass":
    subprocess.run([sys.executable, "-B", helper, "finalize", "--run", run], check=True)
```

## Effort and budgets

### Decomposing coupled work

Choose the smallest independently testable behavior with a fixed input/output or state transition. One or two files, or one abstract "observer/state transition", can still contain several independent mechanisms: a stop boundary, callback protocol, per-record semantics, traversal/skip events and provenance. Estimate the executable paths and test fixtures needed to falsify those requirements, not just file/behavior count. Before delegation, state the current deliverable, dependencies, acceptance/commit points where relevant, deferred requirements and the exact declared test that demonstrates this layer. Put these in the existing `goal`, `acceptance`, `constraints` and `interface_contracts`; do not invent unvalidated dispatch fields.

For an API managing stored resources, a useful sequence is:

| Run | Fixed boundary and acceptance |
| --- | --- |
| Preview/catalog serialization | Actual producer JSON, empty/error cases, consumer-visible field shape |
| Commit/activation | Owner/token acceptance and final commit points; real temporary storage and startup reload |
| Delete | Protection checks, request identity and persistence under its own state transition |
| Restore | Restore-specific preconditions, ownership and persisted result |
| Consumer integration | Generated producer data drives rendering/requests; surrounding regressions |

Adapt this split to the project: do not create all five runs for a simple change, and do not separate code that must change together to preserve an invariant. Astra freezes the boundary; DS implements it; Sol reviews the actual diff and tests. When runs share files, apply/test/review the dependency first, then prepare the next snapshot against the latest state. Independent writers need separate snapshots and non-overlapping paths.

For a first-candidate timeout with repeated reads and no useful changes, inspect the missing boundary/context and narrow the deliverable before retrying. A useful first candidate advances acceptance; a placeholder written to reset a timer does not. Raising effort or waiting longer is justified only by remaining reasoning needs, not file count or the mere fact of a timeout. Existing budgets and the optional single-resume ceiling remain unchanged.

#### Deliver a tested core before diagnostic breadth

For an observer/adapter joining existing code, an illustrative sequence is:

| Layer | Current acceptance | Explicitly deferred |
| --- | --- | --- |
| Executable core | Public call reaches the authorized real helper/producer path; its actual return value satisfies the consumer protocol; required identity/stop/exception/lifecycle invariants hold; minimum contract state categories and conservation checks pass | Additional traversal, skip and provenance detail that is not required to make this core safe or interpretable |
| Additional observations | Add one coupled group of per-record details or ordered view/skip events, retaining the core tests | Remaining independently testable observation groups |
| Evidence completeness | Complete the requested source/depth provenance and export assertions, retaining all earlier checks | Nothing required for final delivery |

Adapt or merge layers when an invariant genuinely requires it; these are not three mandatory runs. In a four-category depth observer, for example, core acceptance can bind the actual two helper returns to the four declared buckets and their totals before adding every view/skip/source event. This is an example, not a required taxonomy for other projects. Keep required stop, source identity, exception handling and resource restoration in the core; do not defer safeguards simply to get green tests.

Maintain a requirement ledger in `acceptance` or the selected contract: each original requirement belongs to the current layer or a named later layer. Give the worker an unambiguous current-layer contract, not "entire contract" while verbally asking for only its core. A layer PASS means only that layer passed; Astra cannot declare the user's whole task complete until every required row is implemented and validated. Later layers use a fresh snapshot after the dependency's accepted changes, including its regression tests. Do not parallelize writers to the same files or remove earlier assertions to fit a budget.

A "pure core" or two-file task can still couple several algorithms and output schemas. Before dispatch, name the smallest independently testable slice: its actual callable/return contract, an authorized frozen input selector, source-supported frame/units, an independent expected assertion, and the existing declared test argv. Supply bounded authoritative source locations and input identity so the worker need not rediscover a large archive schema. If those facts are missing, resolve the concrete gap before dispatch; do not invent a fixture protocol. The first public boundary is the declared slice's API, not necessarily the final report's complete API. For a saved-pose audit, projection of one authorized saved pose onto its fixed points may be a separate real layer before multi-pose/domain comparisons, membership and summaries, when the invariants permit that split. Keep all later obligations in the parent ledger. This is a pre-dispatch scope decision, not permission to stub a completed API, drop prepared acceptance, reset a clock, or grant another recovery after the existing allowance is exhausted.

For callbacks/tracers/adapters, the first real integration test should consume the returned object exactly as the real caller does. Merely constructing it or testing an internal helper does not detect a wrong callable/return protocol. Use only producer/helper execution authorized by the task: a permitted pure or AST-extracted fragment may be exercised with scoped external boundaries; do not import a heavy archived script, run a real case or regenerate experiments to obtain an early test. Preserve the original source-supported predicates rather than inventing new semantics.

#### First declared test checkpoint

Before `prepare`, Astra names the first executable public-path test in the current layer and its existing `test_commands` argv. Prefer the boundary most likely to invalidate the whole candidate: actual backend construction/binding or actual producer data reaching the consumer, with an expectation derived independently from the contract. Test that core before building a broad validator or report inventory; a large green suite that mocks away this boundary is insufficient. Keep that argv self-contained and runnable early with the task's real test framework; add the remaining layer tests under the same declared command as implementation progresses. A partial suite run is early feedback, not final acceptance or a substitute for all current-layer requirements.

Classify the observed result before counting the checkpoint:

| Observed evidence | Checkpoint and next action |
| --- | --- |
| Intended test loads and exercises the current layer's real public function or producer-consumer boundary against an independently derived expectation | The checkpoint is reached; a behavior-level assertion/protocol failure is useful RED. Repair that boundary before widening scope. |
| Missing test module, import/setup-only failure or all-skipped suite | The command ran, but the real checkpoint is still unmet. Preserve diagnostics; implement or repair the owned core/test and rerun the declared command. Report BLOCKED/NOT VERIFIED only for an actual missing prerequisite or authoritative fact. |
| Intentionally observed missing-function TDD RED | Keep this valid development observation; it does not yet show that the public call ran. Continue to the executable core and behavior-level check. |

A loader-generated `_FailedTest` can print "Ran 1 test" without running any intended test. Test counts, exit zero or a file's existence alone are insufficient. Do not manufacture imports/fixtures or waive acceptance to obtain a checkpoint.

As a planning default, aim to **start the first declared test by the earlier of one third of the total attempt budget or one third of the candidate closeout window after the first observed difference**. For default low/high/max this gives a from-start checkpoint of 300/600/800 seconds and a post-change checkpoint of 100/200/300 seconds. The from-start checkpoint prevents a late first edit from postponing all executable feedback. Use the supervisor/attempt start as the time origin, not the latest read, steer or first edit. These are coordinator planning checkpoints, not new enforced timers, measured model-performance guarantees or task JSON fields. Record the chosen target and reason in existing `acceptance`/`constraints`; a stricter task checkpoint wins. Account for known test duration and reserve time for a repair, complete rerun and handoff before the unchanged deadline. If the minimal meaningful test cannot be ready that early, reduce the current layer before dispatch rather than plan a large untested implementation. A target-only test that cannot run locally remains NOT VERIFIED and must have a named authorized coordinator check; do not invent a local replacement.

Observe the actual Bash request and full result/log: a steer ACK, test-file write, hash check or worker statement does not establish that a test started or completed. A first test failure is useful feedback. Fix its earliest shared interface/protocol failure first, rerun the exact declared command, and inspect the actual result before expanding observation breadth; do not spend the remaining window adding features on top of a broken core. Source/hash verification belongs in the authorized declared test or coordinator preparation, not an extra worker probe when the task permits test-only Bash. No alternative test argv or read-only probe is implicitly authorized by this checkpoint.

When only the target can exercise the boundary, plan a minimal completed slice followed by a coordinator-owned target checkpoint before broadening the next slice. Wait for worker exit and all owned jobs to finish; freeze the selected candidate bytes and modes with a manifest. Within existing user authorization, the coordinator may run the exact target-only command against a separately owned isolated target workspace with the required real dependencies. Verify copied source identity before and after the check, and retain target/runtime identity, argv, full logs, exit status, executed/skipped counts and the boundary reached. Do not test a changing worker snapshot, overwrite shared business code, access a target from DS, or treat missing environment/authorization as success. Without an authorized isolated workspace, report the checkpoint pending.

This is a manual diagnostic checkpoint, not a new helper command or an apply/review bypass: `team_dev.py test` still requires the existing applied-target state. An isolated checkpoint does not populate `tests.json` or replace final target tests, process review or Sol acceptance. If a checkpoint fails, preserve it and prepare a focused repair from the frozen candidate; do not patch the active run or renew its budget. Any later source change invalidates affected checkpoint evidence. No additional parallel worker or automatic remote deployment is introduced.

At existing status observations, compare usable core/test artifacts, the boundary actually reached and newly resolved authoritative interface facts. Repeated reads or streaming output with none of these signals no executable progress; zero diff while resolving a concrete interface question is different. The numeric checkpoints are planning limits, not instructions to wait until then. Do not infer network/FRP failure from either signal. Separate an over-coupled assignment from the worker's failure to implement its known core; narrowing later slices must preserve every original requirement in Astra's ledger.

For a missed checkpoint or established no-progress signal, the sole lifecycle owner gives at most one focused instruction for this incident, including any earlier steering: produce the smallest safe core/test within the current task or report the concrete blocker and finish. Judge actual artifacts/results at the next existing status observation; an ACK or promise does not reset the assessment. If nothing advances and no test is active, the owner may cancel and reassess scope under the existing recovery limit; verify worker exit and resource disposition before conflicting work. Do not interrupt an active test merely for a reminder, create a numeric timer/automatic cancellation rule, repeatedly steer, or renew budgets/recovery allowances.

A `candidate_closeout_deadline` failure stays failed and cannot be resumed through the helper. A fresh task after failure must be materially narrower or follow an independently validated takeover; do not reset the same oversized task, repeatedly restart, or extend its frozen budget to bypass the stop. Do not force a meaningless test or skip required acceptance merely to hit the checkpoint.

### Choosing effort

Astra assesses the task before dispatch, records the reason, and selects `worker_thinking`. Consider ambiguity, coupling, algorithmic reasoning and available tests. Do not classify from file count alone. Use `low` for clear small fixes, `high` for bounded algorithm/concurrency/integration work, and `max` only when difficult reasoning remains after splitting. A large cross-cutting task needs decomposition before extra effort. These are coordinator judgments; the helper is a deterministic budget resolver, not another model or a semantic task classifier.

For **new runs**, `budget_mode: auto` selects these initial local policy values (seconds):

| DS effort | Reminder without tool progress | Stop without tool progress | First candidate deadline | Total attempt deadline |
| --- | ---: | ---: | ---: | ---: |
| low | 120 | 300 | 420 | 900 |
| high | 240 | 600 | 900 | 1800 |
| max | 360 | 900 | 1200 | 2400 |

These budgets are adjustable local heuristics, not provider guarantees or measured high/max performance. Greater effort can increase latency; neither more effort nor more waiting repairs a transport failure. Repeated reasoning-only stalls call for inspecting scope/context and preserved evidence before another run.

`policy --task` previews the resolved policy without credentials, model calls, SSH or writes. `prepare` records it in both task.json and metadata.json as `execution_policy`; `status` exposes that snapshot. `start`, `run` and `resume` validate the frozen values without recalculating today's profiles. To change effort or budget, prepare a new task; never edit an active run's JSON. Profile defaults live in `scripts/execution_policy.py`.

`auto` replaces any copied numeric progress/timeout/closeout fields with the chosen profile, so an old low budget cannot silently constrain a newly selected high effort. Omit numeric fields in normal auto task files. For intentional numeric overrides use `budget_mode: custom`; missing progress keys inherit the chosen effort profile. For example, high with `progress: {"stall_seconds": 720}` keeps its 240-second reminder and 900-second first-candidate deadline. An explicit shorter total is permitted and wins when reached first. Total timeout must be an integer from 10 to 3600 seconds; all progress intervals must be finite positive numbers, with warn below stall.

Compatibility: absent `worker_thinking` selects low. `off`, `medium` and a literal thinking value `auto` are rejected. Absent `budget_mode` selects custom if `progress`, `timeout_seconds` or `closeout` is present, otherwise auto. Absent `effort_assessment` gets a visible default attribution; Astra should supply its own reason. Assessment `by` accepts astra/sol/user/default, with a nonempty reason up to 2000 characters. This is an audit claim, not authenticated identity. Already-prepared legacy runs without an execution_policy retain their previous values (historical missing-field defaults: 120/180/240/600 seconds), including on resume; they are not migrated automatically. Sol stays at max independently.

Read/grep churn can still hit the first-candidate deadline. Successful edit/write events or actual allowed-path Git changes count as a candidate; this is a progress signal, not proof of correctness. Tests executing as a tool are exempt from idle/first-candidate checks while active, but remain subject to the overall timeout and, for new v2 preparations, the candidate closeout deadline. The overall timer is checked between bounded RPC operations; allow up to the RPC request timeout (10 seconds) plus abort/cleanup grace. Startup readiness stays bounded at 30 seconds. These RPC transport/startup limits do not scale with reasoning effort. `test_timeout_seconds` is a separate target-test budget and is unchanged by effort selection.

`steer` queues an instruction; the receipt is `controls/<request_id>.ack`. Delivery usually happens at an OMP tool boundary, so steering cannot be relied on to immediately interrupt a current reasoning segment. `cancel` requests an RPC abort and process-group cleanup; inspect status until terminal. Neither queue acceptance nor RPC ACK means code completion. Only a terminal `agent_end`, expected model evidence, tool usage, final response, and all existing delivery gates permit a result to advance.

For runs without a pre-execution gate, `resume` is allowed only for stopped unsuccessful RPC attempts with a saved session, before any application to the target, and only when all policy, journal, resource and baseline checks pass. Strict gate runs use a fresh preparation instead, as described in the [bounded recovery route](#bounded-recovery-route). It rechecks target identity, HEAD and selected-file baseline, archives old attempt evidence into `attempt-1/`, preserves the local snapshot and OMP session, and launches one more bounded attempt. Original file scope and acceptance still apply; the instruction should narrow the route, not relax acceptance. There is no automatic infinite retry. After the second failed attempt, Astra inspects partial work and prepares smaller tasks or explicitly explains taking over. If the task is too broad, split it immediately instead of resuming. A dead/unknown supervisor needs inspection and cleanup before recovery; `cancel` is a request, not a guarantee that an already-dead supervisor can act.

One resume is an upper bound, not a required step. When a run only reasons without a usable candidate, reassess its scope/context before deciding to resume. If Astra takes over, retain the failed worker evidence and report that ownership honestly; do not manufacture worker completion or finalize the failed run as DS success. In a resumed attempt, `first_write_at` can come from scanning a preserved candidate, so it is not necessarily fresh-code latency.

`termination.json` records the stop reason, terminal-event flag, elapsed time, natural child exit code when observed, and safe client-error details. Unsuccessful attempts also write `failure.json`; resume archives both. Reasons distinguish `tool_idle`, `first_candidate_deadline`, `candidate_closeout_deadline`, `total_deadline`, callback/protocol failures, transport/process exit and cancellation. Client exceptions retain their class and traceback frame locations without exception messages, locals or payloads. Model errors in `worker-result.json.errors` are separate from `client_errors`; an empty model-error list never proves that the client or transport succeeded. `worker_evidence_invalid` means a terminal event lacked the required delivery evidence.

Progress distinguishes thinking, output text, tool arguments and unknown streaming. `stream_chars` counts received delta characters by kind without recording their content; characters are not tokens or billing evidence. These diagnostics help separate local failures from long reasoning. They do not prove network health, provider-side effective effort, or semantic progress. Stream counts do not extend any budget; the new candidate closeout window below is independent of the idle/first-candidate exemptions.

### Candidate closeout

New `prepare` calls freeze execution policy v2 with `closeout` in task and metadata. Existing execution v1 or unversioned runs keep their original behavior; this version is independent of process-evidence v3/v4. The timer starts on the first actual allowed-path snapshot difference, not an edit/write ACK. Further edits, reverting the diff, reads, reasoning and steering ACKs never reset it. It measures time available to finish implementation, declared local checks and terminal handoff, not whether a test was attempted or passed.

| DS effort | Reminder after first difference (seconds) | Closeout deadline after first difference (seconds) |
| --- | ---: | ---: |
| low | 180 | 300 |
| high | 360 | 600 |
| max | 540 | 900 |

These are initial local heuristics, not provider limits or empirically optimal settings. Reserve validation time during decomposition. If declared tests take longer, choose explicit `budget_mode: custom` and `closeout: {"warn_seconds": 480, "deadline_seconds": 900}` (for example), or split the deliverable before preparation. Each interval must be finite, positive and at most 3600 seconds; warning must precede deadline. Partial custom fields inherit the effort profile. The original total/idle budgets still apply and can expire earlier; no budget is automatically extended. `policy --task` previews all numbers without dispatch.

`progress.closeout` exposes first-candidate time, age and the frozen window. At the reminder threshold the coordinator sends at most one closeout steer, only while no tool/async job is active, to avoid backgrounding a test merely for a reminder. The warning records `remaining_seconds` and gives an approximate remaining duration sampled before the RPC call; delivery may be later, so this is descriptive, not a fresh timer or promised allowance. It asks for the compact complete ledger once current exact tests and their complete results have been inspected, without rerunning an unchanged passing candidate or polishing harmless warnings. Required corrections still need affected tests; unfinished acceptance remains explicit NOT VERIFIED. The ACK remains queue acceptance. If busy, defer the reminder without extending the deadline. Active tools and pending async results still consume the window; at expiry stop with `candidate_closeout_deadline`, persist evidence and abort through the existing bounded cleanup. This may interrupt a valid long test; configure that case beforehand. Cancellation/RPC/process violations retain their original earlier-priority reasons. As with the total timer, a terminal event drained in the same loop is handled as completion before deadlines; polling/RPC cleanup add bounded grace. None of this guarantees remote descendants have stopped.

Keep brief acceptance/evidence notes during implementation and reserve time for result reads and the final report as well as tests. After a completed test, inspect its actual exit and complete results next; for a logged call, read its saved files. Finish remaining required checks, then reconcile the ledger and hand off directly. State shared commands, counts and log paths once, referring to them from compact requirement rows; preserve every clause and distinct blocker. Omit code walkthroughs, copied implementation and future-tense narration of work already done. Repeat checks or reopen implementation only for a concrete unresolved requirement, changed source or new failure; avoid optional polishing, broad speculative inspection and rereading unchanged source. A later source change requires the affected checks again. This does not waive missing coverage, required visual checks, target-only verification, pending async results or scratch/process disclosures. Wait for pending jobs under the existing async protocol; if a requirement cannot be completed, state the blocker and incomplete status instead of calling the task accepted. No new timer, automatic early stop or test-output-based success gate is added. If this guidance was already present in a failed run, preserve that prompt and treat it as evidence that another reminder alone has not demonstrated a timing fix.

A closeout failure is not a model reasoning timeout, a network diagnosis, or proof that no tests ran. It means the attempt did not hand off within the configured candidate window. Inspect real tool results, pending jobs and the preserved candidate. Compare the last test completion and required result-read times with the deadline before attributing delay to post-test self-checking; a passing test close to expiry may leave only seconds for handoff. Passing logs without terminal completion do not make that failed worker successful, and a rejected or empty process-evidence output is never a PASS binding. The helper rejects resume when this is the recorded failure reason; use a smaller fresh task based on reviewed current work or an explicitly disclosed independent takeover. Other permitted resumes retain their frozen policy but start a new attempt clock, at most once; an existing candidate starts that window on the first scan. Do not repeatedly cancel/resume to enlarge the window. Keep every failed attempt and never finalize it as worker success after takeover.

### Exact Bash mode

For a task whose Bash scope is only its declared tests, set this input before `prepare`:

```json
{"worker_bash_mode": "declared_tests_only"}
```

Omitting it selects `standard`, preserving the existing observed-command checks. Natural-language restrictions are not automatically classified. Astra must select the strict mode when giving a tests-only contract; this does not add Sol preflight or a second planner. New preparation freezes `worker_bash_policy` v2 in both task and metadata, independently of execution policy v2. Standard tasks use process policy v3; new strict tasks use process v4 and `worker_bash_gate` v1. Historical strict runs with process v3 remain observational. Frozen Bash v1 retains its original command/timeout-only rule and exact audit schema; preparations without either Bash marker also keep their original behavior. Do not edit old runs to retrofit or reclassify their completion.

Strict mode permits only exact strings from `worker_direct_test_commands` or `worker_logged_test_commands` in the prepared prompt. Direct strings use `shlex.join` on the exact test argv with `env PYTHONDONTWRITEBYTECODE=1`; logged strings use the existing status-preserving full-output envelope. Only leading/trailing whitespace is ignored. Bash arguments may have `command`, optional finite numeric `timeout` in `(0, 3600]` seconds, and in v2 an optional `cwd` copied verbatim from `worker_bash_snapshot_cwd`. Omitted cwd uses the OMP session launched at that snapshot; an explicit cwd must be the identical frozen absolute snapshot string. No path normalization, symlink/variable/URI expansion or relative alias is accepted. `.` and a different run's snapshot are rejected. Other execution controls, including `pty` and `async`, remain rejected. This does not extend the total/closeout budgets. An alternate interpreter, `cd`, appended command, pipeline, modified envelope, `wc` or manual Python probe fails matching, even with `-B` and even if read-only. Use read/grep/glob tools for JSON, source and saved-log inspection. If those cannot supply needed context, report the blocker; the coordinator can prepare a bounded summary or a fresh appropriately scoped task.

Prepared command SHA-256 values and v2 snapshot cwd are frozen and regenerated from the task argv and run's canonical path. Start/worker/resume/delivery checks reject partial, changed or inconsistent copies. Commands beyond the existing 32,768-character audit limit cannot be prepared in strict mode. Missing, oversized or unsupported-argument tool requests cannot establish permission. Compact events store `exactBashAudit` with fixed status and command hash; v2 separately records `command_match`, `cwd_status` and allowlisted `argument_issues`, without raw arguments/paths. Progress/result include `exact_bash` counts; v2 observations add `command_match_counts` (matched/not_matched/unavailable), because an argument-rejection status alone does not rule out a simultaneous command mismatch. Pure v1 summaries keep their original schema. Exact parameters remain in private tool evidence. `process-evidence` includes the full nested `exact_bash` summary and policy hash; Sol must copy the complete binding as before. Matching is permission evidence only: it cannot show that tests passed, were meaningful, or that invoked programs had no side effects.

That legacy path is **stop after observation**, not pre-execution interception. New strict tasks use the [v4 gate](#pre-execution-bash-gate): two prevented requests may be corrected; the third stops. Strict mode bounds Bash requests; other tool behavior and code inside an allowed test still need existing scope checks, real test receipts and review.

In the observed v1 cwd case, private-argument reinspection established that the prepared command matched exactly and the cwd was the current snapshot, but the extra key violated v1. The shell had already printed its log-directory marker; empty logs and a missing `exit-code` left the test outcome unverified. Read-only `diagnose` distinguishes argument-only rejection when complete matching-command counts support it, simultaneous command/argument rejection when mismatches are recorded, and argument rejection with command matching unverified for v1 or missing/incomplete counts. The logging envelope, strict command allowlist and historic failure classification are unchanged; this is a prompt correction, not a read-only Bash exception.

In strict mode, all worker source changes use native `edit`/`write` within `allowed_paths`; inspect the actual current text with read/grep/glob before editing. ### Failure diagnostics

New workers write `startup.json` and embed it in live progress. It separates local supervisor entry, RPC start/ready, checked model state, prompt call/ACK, first RPC notification, first assistant event, first positive model delta and first tool call. Milestones are elapsed monotonic seconds within that attempt. `message_start` is not a token; user-message echoes and `agent_start` are not model output. A positive thinking/text/toolcall delta is observed stream content, not a billed-token or provider HTTP timing measurement. Prompt-call records invocation of the local RPC API; its ACK only proves local OMP acceptance. Provider HTTP request start remains unknown without separate authorized instrumentation.

Progress before model output now identifies `rpc_starting`, `checking_model_state`, `awaiting_prompt_ack` or `awaiting_model_output`, instead of using `starting` for all of them. At the existing idle-warning threshold, if neither a positive model delta nor a tool call has been observed, write `watchdog-warning.json` with `action: observe` and the startup milestones; do not automatically send the “write a candidate now” steer. If model content/tools have already been observed when that threshold is first reached, use the existing bounded steering reminder. Either action consumes the one automatic warning for this attempt; later model output does not trigger a second automatic steer. Explicit coordinator steering is still supported. No deadline, effort mapping or automatic retry is added or extended. Cancellation stays `cancel_requested`; waiting without errors does not diagnose networking or slow reasoning.

`first_output_wait` in progress, the no-output warning and read-only diagnosis separates an accepted prompt with no assistant event from an assistant header with no positive delta/tool. Its wait age starts at the local prompt ACK; its budget continues to use elapsed time from supervisor entry. For a recorded zero-tool, zero-candidate attempt with complete policy evidence, `stop_at_elapsed_seconds` is the earliest existing idle, first-candidate or total threshold. This is a conditional watchdog threshold, not a provider SLA or an exact process-exit time; bounded RPC and cleanup grace still apply. Readback `remaining_seconds` describes the saved observation time, not a live countdown. Live guidance uses the actual monitor limits (`budget_basis: live_watchdog_limits`); readback requires a supported saved policy version and complete valid timing fields (`saved_execution_policy`). Missing/invalid warning or total thresholds do not yield a countdown. Valid long custom progress intervals remain subject to the total attempt limit.

Before the warning threshold, wait only within the existing bound. At a no-output warning, inspect evidence and either continue within that bound or explicitly cancel; repeated steering and relaunching do not establish progress. After cancellation/termination, the field becomes `ended_without_output` with no remaining wait recommendation. Verify the recorded local process identities have exited before takeover, retain the original stop reason and failed run, and follow the existing bounded recovery rules. Strict gated runs cannot resume in place. If takeover is already underway, do not launch another worker merely because diagnosis mentions fresh preparation. Missing/invalid milestones or missing policy leave observations/budgets unknown; a saved candidate may be subject to a separate closeout deadline. This field never overrides observed HTTP/RPC errors, diagnoses their cause, changes deadlines, authorizes a retry or proves cleanup.

For historical runs, `diagnose` can infer limited startup evidence from the existing RPC-state and compact event log without writing them. Exact ready/prompt-ACK timestamps cannot be reconstructed. Legacy scans are capped at 16 MiB/100,000 records (4 MiB per record); missing/truncated/invalid logs cannot prove absence of model output. The collector never includes payload text in its startup output. `startup.json` joins the attempt archive on resume, and the next worker resets its milestones. Existing in-memory supervisors are not retrofitted or restarted for telemetry.

`diagnose --run` is read-only and needs no task configuration, private credentials, model call or network access. It reads the saved metadata/progress/termination/failure/result JSON files plus startup/RPC-state observations, returns allowlisted categories and counts, and never copies raw error messages, final text, tool arguments or model reasoning. Stopped-run `status` includes the same summary. Missing or unreadable records are explicit; inspect original evidence privately if a category is unclassified. Classification is a diagnostic heuristic, not an authenticated cause or a delivery gate.

Read these layers together:

- `stop_reason` is the coordinator's final trigger/rejection, such as `tool_idle` or `worker_evidence_invalid`.
- `rpc_termination_reason` and `terminal_agent_end` describe RPC lifecycle completion. A terminal event and local exit zero can coexist with failed model streaming or an empty final response.
- `model_error_kinds` distinguishes recognized HTTP rejections from socket closure, stream closure before finish_reason, inter-event stall and first-event timeout. Diagnostic v2 reports `model_http_error_count`, `model_http_status_counts` and `model_stream_fault_count` separately; HTTP errors never inflate stream-fault counts. `rpc_client_fault_count` separately covers local callback/protocol/transport exceptions; snapshot violations are not counted as network faults. Mixed HTTP/stream/RPC observations retain each count and use `model_http_and_transport_faults_observed`; HTTP alone uses `model_http_errors_observed`.
- HTTP classification conservatively reads a leading 400–599 status (bare, `HTTP 404`, `HTTP/1.1 404`, or `Error code: 404`) from saved error text. A 404 containing “Endpoint is unavailable” becomes `http_endpoint_unavailable`; other 404s, 401/403 access rejections, 429, 408, remaining 4xx and 5xx have separate fixed categories. A recognized leading HTTP status takes precedence over stream-related words inside its body. Embedded numbers, endpoint wording alone and malformed/non-string errors stay unclassified. This is a text heuristic, not authenticated response evidence: even a 404 with a `server_error` body cannot determine whether the URL, model route, account access, proxy, gateway or upstream service is at fault. Categories never copy the body or credential values.
- `worker_evidence_blockers` explains missing/invalid model, terminal, tool, final-response or error evidence using the existing worker requirements. A final response must be a string containing non-whitespace text: `final_text_state` distinguishes missing, invalid-type, blank and present values, without exposing the text. Empty strings, spaces and newlines all produce `final_text_missing`; content presence alone does not establish useful code or successful tests. Candidate progress is reported separately and does not prove a useful diff. The diagnosis does not reinterpret or clear any failure.
- `output_observation` combines saved changed-path observations with final-text presence: `recorded_changes_and_final_text`, `recorded_changes_only`, `final_text_only`, `no_changes_or_final_text`, or `changes_unknown_with_final_text` / `changes_unknown_without_final_text`. It never scans the current snapshot or assesses report completeness. Missing/malformed changed-path lists remain unknown; an earlier write with an empty last saved diff is not proof that a candidate remains. Read `candidate_observed` as a progress signal, not current file verification.
- OMP `auto_retry_*` events occur inside an attempt and are separate from the coordinator's optional bounded recovery (an eligible same-run resume or a fresh preparation for a strict run). New compact logs preserve retry attempt/delay/success and an allowlisted error category without the payload. No retry policy is changed.

`provider_access` v1 makes three different evidence levels explicit: local model selection, saved request configuration, and generation observations. An expected `opencode-ds/deepseek-v4.1-flash` selector in `rpc-state.json` yields only `expected_selector_observed`. For new worker processes, the existing `get_state` response also saves `request_configuration` before prompting: API mode and a fixed endpoint-family label (`opencode_inference_openai_v1`, `opencode_zen_v1`, or `other_or_unknown`). Only exact known base URLs, allowing trailing slashes, receive named labels. Full URLs, arbitrary hosts/paths, query values, userinfo, headers and keys are never copied into this new record. This describes local OMP model configuration, not a captured wire request or an endorsement of either endpoint. Older runs remain `not_recorded`; never fill their historical route from today's profile. Malformed route records remain `unreadable`.

`generation_observation` separately reports saved HTTP errors, recorded model output, no usable completion, or unknown. Any saved HTTP errors take precedence over output presence and remain failures. Even recorded model output does not establish successful tool execution, acceptance or current availability: `current_service_health` stays `unknown`, and `provider_http_request_observed` stays null. An error-only assistant event or prompt ACK does not count as generation output. This adds no network preflight, health probe, fallback, retry or new delivery gate.

For a leading HTTP 402, diagnostics distinguish `http_insufficient_account_funds` when the saved text explicitly contains "Insufficient account funds" (case/whitespace insensitive), from generic `http_payment_required`. That wording without a leading 402, or inside another status, does not establish this billing category. `provider_access.billing_observation` reports `insufficient_account_funds_reported`, `payment_required_reported`, or `not_observed`; `account_balance_verified` remains false. This is a provider-message observation, not proof of which gateway/upstream account lacks funds, its current balance, or service health. Counts cover saved error entries, not distinct authenticated requests. Mixed stream/RPC faults remain visible.

When either 402 category is recorded, `request_failure_guidance` defers provider retry pending evidence that the reported billing issue is resolved. Do not repeat the same endpoint, change proxy/credentials/provider, increase effort/deadlines or add a health probe solely in response to that error. This diagnostic authorizes none of those actions and changes no OMP retry policy. Follow the existing stopped-worker/candidate takeover procedure: keep failed identity, saved errors and actual test status. Two saved files, nonempty final text, `agent_end` and exit zero cannot substitute for tests or worker success; zero recorded Bash calls is no recorded Bash test execution, not a passing suite. A separately tested/reviewed Astra takeover does not relabel the worker. Existing candidate inspection and recovery eligibility checks still apply, and no later retry is authorized merely by this advisory.

A record with `process: not_started`, `delivery: prepared`, and no saved runtime files/metadata is diagnosed as `prepared_not_started` / `not_started_in_saved_records`. Do not count a superseded preparation as another provider failure. Runtime evidence conflicting with those preparation labels is explicit and must not suppress saved errors; partial or missing records cannot prove a provider request occurred. These are observations of retained local records, not protection against manual evidence deletion.

For stream faults, first inspect the local OMP request path, proxy/gateway timing and provider availability using bounded authorized checks. Repeating the same implementation, steering it to write immediately, raising reasoning effort or increasing the task deadline does not repair stream closure. If the connection path is still uncertain, retain that uncertainty and let Astra take over when appropriate rather than auto-retry indefinitely. Without stream/client errors, a read-only deadline is evidence of no candidate within the budget, not proof of healthy networking or of the model's internal reasoning cause.

For HTTP rejections, `request_failure_guidance` asks for endpoint/model/access inspection before considering recovery and keeps root cause `unknown`. Inspect the configured base URL, API mode and model ID without printing secrets; check the provider's current documentation and, when useful, bounded metadata requests. Local OMP selector acceptance only confirms local selection. A public models GET can differ from an authenticated chat POST; catalog inclusion does not verify account access, generation, streaming or tool use. An undocumented `/models` 404 does not establish that its sibling completion route is unavailable. Route differences are leads, not permission to switch endpoint/account, send project payloads or start more workers. Preserve the original failure and recovery allowance; effort or deadline increases do not fix a rejected request. This advisory does not launch retries, validate recovery eligibility or supersede `recovery` (including active-run inspection, strict fresh preparation and saved-candidate takeover). Existing supervisors keep their loaded code; old run evidence is not rewritten by a newer diagnosis.

### Bounded recovery route

Choose the route after the worker has stopped and evidence/resources have been inspected. `diagnose.recovery` is a metadata-only hint: a saved `worker_bash_gate` marker or process-policy v4 signals that same-run resume is prohibited, even when no Bash call or denial occurred. Absent markers do not prove eligibility. Missing attempt numbers remain unknown. Diagnosis does not validate task/metadata agreement, session availability, journals, resource disposition, snapshot integrity or target identity/baseline; launch/resume checks remain authoritative. For an active or unknown process it only asks for state inspection, not a new worker.

| Saved run | Bounded next step |
| --- | --- |
| Failed run with recorded changes, with or without a final report | Inspect the preserved candidate and resources first; useful work can enter an independently recorded takeover. Missing or stale candidate evidence still needs inspection. Do not relabel the original worker as successful. |
| Strict gate / process-policy v4 needing another worker | Preserve the original run and failure; prepare a fresh bounded task from the current target after inspecting evidence and resources. Do not call `resume`, delete gate markers, or reuse gate nonce/journal/correction budget. |
| Other stopped unsuccessful runs | Optional one-time `resume` only if the task still fits and every existing resume check passes. Closeout, prohibited-request, async or damaged-evidence cases can still require a fresh task or independent takeover. |
| Recovery already failed or scope remains too broad | Stop repeating the same implementation; reassess/decompose or record an explicit independent Astra takeover with Sol review. |

A terminal response after an OMP internal retry can contain a candidate and a useful report while the attempt still has `model_errors_present`. For stopped unsuccessful runs with saved changed paths, the advisory recovery action is `inspect_preserved_candidate_for_independent_takeover`; it does not launch, copy, apply or approve anything, and does not grant another retry. Keep prior stream errors and the failed run intact. Inspect actual source/diff and process/resource evidence, then use a separate coordinator-owned candidate with current target identity/baseline checks, required target tests and independent Sol review under the existing [takeover receipt](#takeover-and-review-provenance). A worker self-report of NOT VERIFIED identifies an unresolved requirement, not a test pass or permission to omit it. Missing target dependencies must be resolved and the required checks run before claiming completion; otherwise report the result as unverified. No text classifier in `diagnose` certifies these claims.

For one unchanged bounded deliverable, allow at most one coordinator-arranged recovery after the initial failed worker. A fresh strict run is that recovery, not a reset of the allowance. Keep a coordinator receipt outside the original run with the original and recovery run paths, failure category, recovery index (`1`), reason and intended scope; reference the original failure in the fresh task's context/constraints. Cross-run accounting is a coordinator procedure, not an enforced global retry ledger in this helper. OMP internal `auto_retry_*` events are recorded separately and do not authorize more coordinator retries. No retry is mandatory.

For an empty terminal response with observed stream faults, retain both facts: lifecycle completion did not supply worker completion evidence, and the fault location remains unknown. Normal SSH reads or target tests do not establish the health of the separate OMP-to-provider stream. A fresh attempt can use the same frozen effort/budgets when still appropriate; neither automatically raise them nor lower acceptance. Repeated faults call for bounded connection-path investigation or disclosed takeover, not an endless chain of fresh runs. Any useful partial candidate remains subject to independent inspection, tests and review; never relabel the failed worker as successful.

OMP nested `task`, advisor and prewalk remain disabled in this worker.

## Pre-execution Bash gate

New `declared_tests_only` preparations retain exact Bash policy v2 and freeze an additional `worker_bash_gate` v2 plus process-evidence v4. Historical gate v1 runs retain their frozen extension, configuration and denial text. Standard-mode and historical runs keep their frozen policies. No server-side OMP installation is needed.

New preparations provide `worker_test_invocations`: numbered `T1.direct`, `T1.logged`, etc. entries with the complete Bash `arguments` object. Copy that object into the Bash tool call. IDs are lookup references, not executable aliases; command hashing still allows only the unchanged prepared direct/logged strings. The gate v2 policy additionally binds the catalog hash; startup validates catalog structure, exact-command coverage and configuration identity. Missing or changed entries fail closed. No new shell wrapper, test selection, probe permission or execution path is added.

Gate v2 denial text reports `command_match`, `argument_issues` and `cwd`, plus a closest reference and zero-based Unicode-codepoint mismatch position/lengths when an unambiguous sufficiently similar entry exists. The bounded hint searches at most 131072 catalog characters, uses stripped strings like the existing command matcher, and may omit a reference; it is not a semantic equivalence test or authority to execute. It never copies raw rejected command text, extra argument names/values or expected command contents into the hint. Recopy the catalog object instead of reconstructing the envelope or correcting a token from memory. Optional timeout/cwd remain governed by the same existing rules. The third denial still stops; a hint never grants a fourth attempt. V1 saved journals are validated with their original denial format, without injecting v2 hints into historical evidence. Gate policy/configuration advance to v2; registration and event-annotation schemas retain v1 because their fields and meaning are unchanged.

Before sending the task, the supervisor checks the RPC model state and a fresh nonce-bound `session_start` registration record. OMP RPC `ready` alone is insufficient. Missing registration, changed extension/rules, unsupported OMP version or evidence failure stops the attempt; there is no fallback to unguarded execution. Upgrading OMP requires revalidating this boundary before changing the pin.

The gate accepts the same exact declared commands and permitted timeout/cwd arguments. It synchronously journals each Bash decision and returns a blocking tool error before calling Bash for rejected requests. The first two denials allow the worker to correct its tool choice. The third denial locks subsequent tools and the supervisor stops with `preexec_bash_denial_limit`. Denials do not count as tool progress or extend existing deadlines. This is a run-wide total of two corrections, not a per-command or consecutive-error allowance. These new attempts cannot resume; preserve the run, then decompose/reprepare or use a separately recorded takeover.

On tested OMP 18.2.8, denied requests still emit `tool_execution_start/end`. A start event therefore does not prove execution. The private gate journal, matching call IDs/arguments, exact blocking result, and pinned extension identify a prevented request. After lockout, read/edit/write and other non-Bash requests also retain tool names, call IDs, full raw arguments and blocking reasons. Their private RPC start/end records are correlated in a hash-bound failure receipt; missing or contradictory delivery stays explicit. Process-evidence v4 binds complete gate/config/extension hashes and cross-checks the ordinary RPC journals. Missing, duplicated, inconsistent or incomplete evidence cannot pass. Successfully prevented requests remain visible under `preexec_gate`; they do not count as executed Bash violations. Sol must supply `process_review.preexec_denial_resolution` when denials occurred. The third-denial limit cannot pass review. Actual executed requests remain subject to the existing process checks.

This protects the Bash tool entrypoint inside OMP, not all operations of the same OS user. It cannot certify the behavior inside an allowed test or the semantics of edit/write tools. Snapshot guard, target tests and independent review remain required. Historical failures are not relabeled.

Offline verification uses the actual installed OMP binary with an isolated agent directory and a scripted loopback provider. It covers non-execution sentinels, correction, lockout, direct/logged nonzero test exits, registration failure, argument parity and evidence tampering. The fixture uses simulated model labels where needed to exercise unchanged supervisor state checks; it is not a DeepSeek availability, network or future-compliance test.
